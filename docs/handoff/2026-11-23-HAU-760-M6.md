## Done and verified

- **Config plugin Android half** (`plugin/src/index.ts`): writes `res/xml/cloud_sync_extraction_rules.xml` (Android 12+,
  `<cloud-backup>` and `<device-transfer>`) and `cloud_sync_backup_content.xml` (11 and lower), each including only
  `file` `SQLite/`, plus the `backupInclude` prop's entries; sets `android:dataExtractionRules` and
  `android:fullBackupContent`. If `<application>` already names other rules (expo-secure-store), prebuild fails with a
  message instead of dropping them. No app on this machine uses expo-secure-store today.
- **Account change**: `accountChanged` / `adoptAccount` already existed on both platforms (M3, M4). M6 change: sign-out
  keeps `account_id`, so signing in to a different Google account afterwards shows `accountChanged` (with the new email
  in `accountLabel`) and nothing moves until `adoptAccount()`. Before, sign-out cleared it and the next account merged
  silently.
- **iOS `signOut`** now turns sync off on the device (`off`, `enabled = 0`) and forgets the engine state; turning it on
  again is a first sync. Before, after "delete iCloud copy" the device kept syncing with clean rows that were never
  re-uploaded.
- **"Delete synced copy" caveat**: JSDoc on `CloudSync.signOut` and `SyncStatus.accountLabel`, plan string
  `syncDeleteCopyHint`, and the example app shows the hint under both platforms' delete buttons. No extra machinery.
- **WAL checkpoint on background** already existed in both drivers; now tested.
- Tests (78, was 72): Drive: sign out then sign in to another account asks first and merges only after adopt, the first
  account's files untouched; an Auto Backup restore onto a new phone gets a new device id and merges, including rows
  written just before the backup; a restore onto a phone signed in to another account asks. Engine: delete iCloud copy
  turns sync off and a re-enable sends every row; another iCloud account after that still asks. Cycle: going to the
  background empties the `-wal` file while signed out. `bun run check` passes.
- **On the Linux worker** (scratch copy, temp AVD `cloudsync-m6` on API 35 google_apis, all deleted after): prebuild
  shows the manifest attributes and both XML files; `assembleRelease` (made debuggable for `run-as`) built; the app runs.
  `bmgr` acceptance: never signed in, two notes added, main file still 4 KB (rows only in the WAL), `bmgr backupnow`
  within seconds (Success; the app was killed), uninstall, install: only `files/SQLite/` came back, `no_backup/` empty,
  both notes shown, a new device id on screen, and the restored `_sync_meta.device_id` equals the new id with both rows
  dirty (read from the pulled database). Home button: `icloud.db-wal` went to 0 bytes.

## Bug found and fixed

The example app crashed on launch ("cannot start a transaction within a transaction"): `SQLiteProvider` reruns
`onInit` whenever its identity changes, on the same shared connection, and the example passed inline functions while
`App` re-rendered (device id state). Fixed with module-level `onInit`s. Every adopting app must pass a stable `onInit`
(added to the plan's rollout step 3). This was the first time the example app ever ran.

## Watch out for

- While signed out the status' `pending` is not refreshed after local writes (the write check runs only in `idle`); the
  example showed "0 pending" with two new notes until relaunch. Cosmetic, not fixed.
- An app that keeps data outside expo-sqlite (Plate Weight and Sonic on MMKV, Paycheck Planner on AsyncStorage) loses
  it from Auto Backup when it adds the plugin unless it passes `backupInclude`.
